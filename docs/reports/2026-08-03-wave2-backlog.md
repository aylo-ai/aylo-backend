## 1. Conflict resolutions

Where two agents disagreed I state both positions and decide. I do not average them.

### C1 — Token encryption: P0 #1 (Security) vs "theater, third priority" (Devil's Advocate)

- **Security (#1, P0):** any DB read — backup, replica, SQL injection, stolen dump — yields full control of every customer's Telegram bot and Instagram DMs.
- **Devil's Advocate (#1):** the same secret sits in plaintext in `Conversation.token` (`apps/assistant/models.py:129`), in the nginx access log forever, and in `/opt/aylo/.secrets/.env` on the same host as the key. An attacker with host read does not need the DB at all. "Compliance cosplay" absent a written threat model, a non-`.env` key store, and a blind-index spec.

**Decision: the Devil's Advocate wins on sequencing; Security wins on the work existing at all. Encryption is P1, scheduled in Round 4, and blocked on T-02 and T-14.**

**What the encryption actually defends against — write this threat model into T-19 verbatim:**

> In scope: theft of a `pg_dump`, a stolen or mis-permissioned backup artefact, a logical-replication subscriber, a read-only SQL-injection oracle, and a decommissioned disk volume. In all of these the attacker obtains database *contents* without obtaining *host process memory or the application environment*.
> **Explicitly out of scope:** host compromise, container escape, and anyone who can read `/opt/aylo/.secrets/backend.env` — for that adversary the key and the ciphertext are equally reachable and encryption at rest buys nothing.

This is a real but narrow adversary, and it is honest to say so. Two of the Devil's Advocate's three "changes my mind" conditions are made mandatory acceptance criteria of T-19 (written threat model; the plaintext duplicates removed **first** by T-02 and T-14). The third — KMS/`sops` instead of an env keyring — is **deferred to a human decision** (§5, H-3): an env keyring in `/opt/aylo/.secrets/backend.env` still raises the bar materially for the modelled adversary, because dump theft is not host access. If the answer is "KMS", T-19 grows by roughly 2 days and slips a round.

### C2 — Making the lookup work: HMAC blind index (Backend #1) vs opaque webhook id (DA kill-list #3)

- **Backend:** encrypt the column and add an `api_token_hash` HMAC-SHA256 column with a unique index, landing *at the same time*.
- **DA:** replace the scheme entirely with an opaque per-integration id in the path plus Telegram's own header secret.

**Decision: opaque webhook id (T-02). No blind index is built.** A blind index preserves a lookup we should not be performing; the opaque id deletes the lookup instead, and only it fixes the access-log leak (G7) and the seq scan at the same time. A blind index fixes neither. This also removes Backend #2 (`AddIndexConcurrently` on `api_token`) from the board entirely — **merged into T-02 as "no longer needed"**, since after T-02 nothing filters on the token value.

### C3 — Perf work: "measure first or cut the wave" (DA #4) vs 15 ranked data-layer findings (Backend)

- **DA:** scale is unverified; indexing hot tables without measurement is how you take an outage during a migration.
- **Backend:** 15 findings, of which the top 5 are S-effort.

**Decision: split the Backend list by class, not by priority.**

| Class | Examples | Treatment |
|---|---|---|
| **Correctness bugs** (wrong behaviour at *any* scale) | check-then-set dedupe race; `tg_dedup:{update_id}` colliding **across bots** and dropping legitimate messages; `LRANGE`+`DEL` losing messages pushed between the two round-trips; unbounded Redis calls in the webhook path; `process_monthly_subscriptions` double-charging | Ship in Round 2 **with no measurement precondition**. These are bugs, not optimizations. |
| **Optimizations** (value is a function of load) | `(conversation, -created_time)` index; dashboard N+1; `CONN_MAX_AGE` | Round 4, and each carries a mandatory `EXPLAIN (ANALYZE, BUFFERS)` or `assertNumQueries` **before and after, pasted into the ticket report**. Index migrations use `AddIndexConcurrently` with `atomic = False`, which is the direct answer to DA's migration-outage objection. |

### C4 — "Meta data-deletion is the real existential risk" (DA #2) vs P1 (Security #4)

**Decision: raised to P0, Round 1b (T-05).** `InstagramDataDeletionView` (`apps/integration/views/instagram_oauth.py:245-265`) verifies the signed request, logs, returns a confirmation code, and **deletes zero rows** — while handing Meta a status URL on `api.repli.uz`, a retired domain, at a path that is not routed in `apps/integration/urls.py`. A handler that lies to a regulator, plus a 404 for the reviewer following it, is a failed app review; `instagram_business_manage_messages` is revocable at Meta's discretion and 7 of 12 modules in `apps/integration/views/` are Meta-only code paths. Severity here is driven by likelihood of product death, not by CVSS.

### C5 — "132 of 144 endpoints unthrottled, no global rate limit" (DA #4)

**Partly wrong, and the correction matters.** `apps/integration/throttles.py` exists and does throttle the OAuth callback and Meta's deauthorize/data-deletion callbacks at 30/min, and it documents a *deliberate* decision not to throttle the webhook receivers (Meta disables a subscription that starts collecting 429s). That reasoning stands.

**Decision: DA's core point survives for the dashboard and tenant list endpoints.** T-06 adds real `DEFAULT_THROTTLE_RATES` for `user`/`anon` and keeps the documented webhook exemption. Critically, this is **blocked on the `CACHES` fix in the same ticket**: with no `CACHES` setting, DRF throttling runs on per-process `LocMemCache`, so with 4 gunicorn workers `otp_send: 5/minute` is really up to 20/minute and resets on deploy (Backend #11). Adding throttles without Redis-backed cache ships a limit that does not limit.

### C6 — Coverage target

Both QA (§1: "100% is not the goal and should never be the gate") and DA (#6: "roughly 400+ tests nobody will read") agree. **No conflict — recorded as settled.** The gate is `diff-cover` at 80% **on changed files only**, against `origin/dev`, with a documented `.coveragerc` exclusion list. No global coverage gate: a 66%→80% backfill mandate produces assertion-free tests.

### C7 — IG token refresh, found three times

Security #6, Backend #1 and UX P0 #2 are **one issue**: `instagram_refresh_token()`'s return value is discarded at `apps/integration/gateways/instagram.py:38`, no beat entry refreshes, and no expiry is stored — so every IG integration dies silently at ~60 days and neither backend nor UI can say so.

**Decision: one ticket (T-10) spanning both repos.** The UX constraint is part of its acceptance criteria and is a real ordering dependency: **the status indicator cannot exist until the backend stores `token_expires_at` and exposes it in the integration serializer.** The frontend half (FE-04) is a dependent ticket in Round 3, not a parallel one.

### C8 — OpenAI `store: True`, retention, and ZRU-547 (DA #3, Security #9)

**Decision: split.** The engineering half — a retention purge beat task, bounding `Message` growth, and making `"store"` a setting rather than a hardcoded `True` at `apps/shared/ai_service/agent.py:234` — is T-20, Round 4. The legal half (lawful basis for a DM sender who never signed our ToS, an OpenAI DPA/ZDR, and whether ZRU-547's data-residency requirement is violated by sending Uzbek citizens' DMs to a US sub-processor) is **not an engineering ticket** and is escalated as H-4. Engineering cannot close it and should not pretend to.

### C9 — Broadcast opt-out (QA P1-8) and language detection (QA P1-9)

Both are **new capabilities the API does not have today**, not defects in existing code. Per scope discipline they are **cut from Wave 3** and listed in §6 Deferred. Opt-out in particular may be a legal requirement in the target market — that is a product/legal call (H-5), not something a Wave-3 agent should invent.

## 2. Definition of done — binding on every ticket below

This block is part of the acceptance criteria of **every** ticket in §3. It is stated once rather than pasted 24 times so the ticket table stays readable; a ticket is not done unless all ten items hold.

1. **Acceptance criteria met and demonstrated** — the ticket's own criteria, shown, not asserted.
2. **Tests written first**, and **each security test fails when the protection is removed** — the report must show the test failing against the reverted protection, not just passing against the fix.
3. **No secrets in code, logs, fixtures, or CI output.** Extend the existing pattern at `apps/shared/tests/test_telegram_webhook_logging.py:21-57`, which already asserts the bot token never reaches captured log output.
4. **Migration is reversible, and existing rows stay readable.** A `reverse` path exists and is exercised.
5. **p95 of touched endpoints is not worse than before** — numbers pasted, or the literal string *"unmeasured — baseline established in this ticket"* plus the baseline.
6. **Strings localized (uz / ru / en)**, no hardcoded copy. Backend uses `gettext_lazy as _` per CLAUDE.md §3.
7. **Error and empty states designed and implemented** (frontend tickets: loading + empty + error + "empty because filtered").
8. **Reviewed by an agent that did not write the code.**
9. **Rollback note written** — one paragraph: what to revert, in what order, and what data is left behind.
10. **Repo conventions honoured** (CLAUDE.md, binding): `success_response` / `error_response` / `raise_validation_error` from `apps/shared/addons/validations.py`, never a bare `Response`; enums from `apps/shared/addons/enums.py`, never hardcoded status strings; one permission class that covers the allowed roles, never a list DRF will AND together; module-level `logging.getLogger(__name__)` with lazy `%s`, never `print()`; the `apps.` import prefix on every internal module and every patch target (enforced by `apps/shared/tests/test_import_paths.py`); dead code adjacent to the change deleted (§4); tests run as `.venv/bin/python manage.py test <path> --keepdb` with the output pasted; a dated change report in `docs/reports/`.

**Where I depart from the round order in the brief, and why.** The brief put P0 security in Round 1 and hardening plus load test in Round 4; that holds. The Round-3 frontend slot is reserved for the one ticket that genuinely has a backend dependency (FE-04 on T-10).

## 7. Top 3 risks to the schedule, and the rollback plan per round

### Risk 1 — T-02 takes the Telegram channel down for every customer

It rewrites the webhook URL scheme, the auth mechanism and the model, and it must re-register `setWebhook` with Telegram for every integration. A bad backfill silently stops inbound messages, and **the failure is invisible from our side** — Telegram simply stops delivering. It is the critical path for T-09, T-14 and T-19; a slip cascades into three rounds.

**Mitigation:** the legacy `<str:bot_token>` route stays live for the whole overlap window (acceptance criterion (d)), so old and new coexist; the backfill is idempotent and resumable; roll out to one internal integration first and confirm a real inbound message before the fleet-wide run. **Alarm on inbound-webhook volume dropping**, since success is indistinguishable from silence.

### Risk 2 — H-1 revocation stalls, and Round 1 cannot close

T-01 cannot close until a human revokes the Google key, and the bot-token rotation needs customer coordination. Agents will be tempted to mark T-01 "done" on the code change alone — which leaves a live private key in public history and a false green on the board.

**Mitigation:** T-01 is explicitly two-phase — the code merges, the **ticket stays open** with an owner named for the human action. The board shows it as blocked-on-human, never as complete. If revocation has not happened by the end of Round 2, escalate rather than continue.

### Risk 3 — measurement-gated tickets get closed with invented numbers

G5 says scale is unverified, yet DoD #5 asks for p95 on every ticket and T-13/T-21 gate on `EXPLAIN` output. The realistic failure is an agent pasting a plausible-looking number rather than saying "unmeasured".

**Mitigation:** DoD #5 accepts the literal string *"unmeasured — baseline established in this ticket"* as a passing answer, so honesty is never the harder path. T-21 is scheduled in the same round as T-13 so a real baseline exists exactly when the optimization work needs it. The cross-review in DoD #8 is done by an agent that did not write the code, and checking for a pasted `EXPLAIN` is a named item in that review.
